## 為什麼需要 CLAUDE.md

Vibe Coding 的重點是「這一個頁面做出來」；但個人網站是長期專案。每次開新對話，AI 都是失憶的：它不知道我的文章要放哪、檔名怎麼取、英文版是誰翻的、哪些資料夾不能碰。

我以前的做法是每次重新講一遍，講漏了就出事。例如 AI 好心幫我手寫英文版，結果跟自動翻譯的 pipeline 打架。

**CLAUDE.md 就是放在專案根目錄的「交接文件」**：Claude Code 每次啟動都會自動讀它（其他工具通常讀 `AGENTS.md`，概念相同，內容可以共用）。規則寫一次，之後每個對話都從同一個起點開始。

## 這個網站是什麼

[datafox.tw](https://datafox.tw) 是我的個人網站，用 Hugo + PaperMod 主題，部署在 GitHub Pages，內容有技術筆記、作品集、Podcast 與每週自動產生的 GitHub AI 趨勢。完整原始碼在 [datafox-tw/datafox.github.io](https://github.com/datafox-tw/datafox.github.io)，而本站的 CLAUDE.md 就在 repo 根目錄：[CLAUDE.md](https://github.com/datafox-tw/datafox.github.io/blob/main/CLAUDE.md)。

## 我的 CLAUDE.md 怎麼設計

我把它分成八個區塊，每一塊都在回答 AI 一定會問的問題：

| 區塊 | 回答的問題 | 沒寫會怎樣 |
|---|---|---|
| 專案目的 | 這個網站為誰而做？ | AI 寫出不符合定位的內容 |
| 技術棧 | 用什麼工具、怎麼預覽與建置？ | AI 亂猜用 npm 或 Jekyll |
| 目錄結構 | 東西放哪？ | 檔案散落各處 |
| 雙語規則 | 誰寫中文、誰寫英文？ | 手寫英文與翻譯 pipeline 衝突 |
| 新增文章 SOP | 檔名、front matter、格式 | 每篇格式都不一樣 |
| 其他區塊規則 | `news/` 能不能手動改？ | 改壞自動產生的內容 |
| 風格與設計 | 能不能引入新套件？ | 專案越長越亂 |
| AI 行為準則 | 能做什麼、不能做什麼、完成前檢查什麼 | AI 越權、洩漏金鑰、擅自 push |

### 幾個關鍵段落

**1. 把專案裡「不明顯」的規則寫出來。** AI 讀程式碼能看出 Hugo 的結構，但看不出「`.zh-tw.md` 是原稿、`.md` 是 Gemini 翻的」這種隱含約定。這種規則最值得寫：

```markdown
| 檔案 | 語言 | 誰負責 |
|---|---|---|
| `名稱.zh-tw.md` | 繁體中文 | 人 / AI 撰寫（原稿） |
| `名稱.md` | English | scripts/auto_translate.py 自動產生 |

新增內容時只寫 .zh-tw.md，不要手寫英文檔，除非使用者明確要求。
```

**2. 用範本取代形容詞。** 與其寫「front matter 要完整」，不如直接貼一份可複製的範本，並註明哪些欄位必填、slug 的格式。AI 會照著模仿，比理解一段描述可靠。

**3. 明確寫出禁止事項與原因。** 例如：

```markdown
不可以做（除非使用者明確要求）
- 修改 themes/PaperMod、public/、resources/
- 讀取、輸出或提交 .env、.env.local
- 手動編輯 content/news/（由每週 workflow 自動生成）
- 更動既有文章的 slug（會破壞舊網址）
- git commit / git push：先給變更摘要，等使用者同意
```

**4. 結尾放檢查清單。** AI 在「完成」之前跑一遍清單，能擋掉大部分低級錯誤：

```markdown
- [ ] 檔名符合 YYMMDD_HHMM.zh-tw.md
- [ ] front matter 欄位齊全、slug 不重複
- [ ] hugo --gc --minify 通過
- [ ] 沒有動到禁止區域
```

## 實際使用：新增這一篇文章

這篇文章本身就是用 CLAUDE.md 產生的。我只下了一句指令：

> 幫我寫一篇文章，介紹怎麼用 CLAUDE.md 建立個人網頁。

因為 CLAUDE.md 已經規定好，AI 自己完成了這些事：

1. 取現在時間，建立 `content/posts/261111_2030.zh-tw.md`（依命名規則）。
2. 產生完整 front matter：`title`、`slug`（英文 kebab-case）、`description`、`tags`。
3. 只寫中文原稿，**沒有**去碰英文檔，因為規則說英文由 pipeline 處理。
4. 用 `##` 分節、程式碼標語言，符合格式規範。
5. 跑 `hugo --gc --minify` 驗證，回報變更了哪些檔案。
6. 沒有 commit / push，等我確認。

之後 push 到 `main`，GitHub Actions 會自動翻譯成英文、部署上線。整個流程我只需要提供**想法**，不用重複講規則。

## 如何延伸：新增一個全新的頁面區塊

規則的價值在於可以延伸。假設我想新增一個 `reading/` 書單區塊，只要在 CLAUDE.md 第 6 節已經寫了：

> 新增頁面區塊：需同時修改 `hugo.yaml` 中 zh-tw 與 en 兩份 `menu.main` 與 `permalinks`，並建立 `_index.md` 與 `_index.zh-tw.md`。

AI 就知道該改哪幾個檔案、不會漏掉英文選單。而做完之後，我再把「書單的 front matter 格式」補進 CLAUDE.md，下一次新增書籍就是一句話的事。**CLAUDE.md 是活的文件，每次踩到坑就補一條。**

## 撰寫心得

- **短而具體勝過長而完整。** 每多一句話都會稀釋重點，只寫 AI 猜不到的東西。
- **寫「為什麼」。** 「不要改 `news/`，因為它由 workflow 自動生成」比單純「不要改 `news/`」更能讓 AI 在邊緣情況做對判斷。
- **用 AI 起草，用自己的專案經驗修訂。** 我是先請 Claude Code 掃過 repo 產生初稿（`/init`），再把踩過的雷（雙語衝突、`slug` 不可改、金鑰不可碰）補進去。
- **當作可版本控管的程式碼。** CLAUDE.md 跟著 repo 一起 commit，規則改了有紀錄，換工具（Cursor、Codex）時改名或建立 `AGENTS.md` 連結即可。

規則寫好之後，維護網站的心態也變了：我不再是「每次叫 AI 做一件事」，而是**在經營一個讓 AI 能自己做對事的環境**。
