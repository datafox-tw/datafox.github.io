## Why I Wanted to Do This

A common misconception about static websites is that 'static' means dead or unchangeable. However, when combined with CI/CD, they can achieve things many people wouldn't expect.

I wanted to do one thing: have a specific section of this website update automatically every week, without me having to manually write anything. My motivations were twofold:

-   First, a pure desire to test how far static deployments like GitHub Pages can go with automation. From data crawling, calling an LLM, to finally committing to the repo to trigger deployment, the entire chain can be completed within GitHub Actions, without any backend server. This in itself is quite interesting.

-   Second, practicality: GitHub Trending is an information source I believe is currently underutilized. Run a top 15 check weekly, filter out irrelevant results with keywords, and then have an LLM summarize the rest for me, automatically publishing it to the website. This way, I don't have to actively track it every week; the information comes to my website itself.

---

## Technical Details

The starting point was finding a clean RSS feed. GitHub doesn't officially provide an RSS feed for Trending, but someone created one: [mshibanami/GitHubTrendingRSS](https://mshibanami.github.io/GitHubTrendingRSS/), which updates daily. The URL format for weekly reports looks like this:

```
https://mshibanami.github.io/GitHubTrendingRSS/weekly/all.xml
```

With the RSS feed, the pipeline structure became clear:

1.  **Fetch Data**: Parse the RSS feed using `feedparser`, taking the top 15 entries.
2.  **Rough Filter**: Filter using keywords (gemini, claude, gpt, llm, ai, etc.) to exclude repositories irrelevant to the personal website's theme.
3.  **Generate Content**: Send the filtered repositories all at once to Gemini 2.5 Flash, asking it to use a single prompt to generate both traditional Chinese descriptions for each project and a set of tags for the entire batch.
4.  **Write & Deploy**: Save the generated markdown to `content/news/`, then `git push` to trigger the existing Hugo deploy workflow.

The entire process is housed within GitHub Actions, set to run once every Sunday at 12:30 PM Taiwan time. There are no continuously running servers, and the cost is virtually zero (the cost of Gemini API for this usage volume is negligible).

## Reflection: Collaborating with Claude

This entire system was built by me and Claude together.

My starting point was just a rough idea: "I want to crawl GitHub Trending weekly and have an LLM summarize it for me." As for how to parse RSS, how to write GitHub Actions YAML, where to set cron timezones, why `GITHUB_TOKEN` can't trigger other workflows... I knew these details existed, but I didn't particularly want to deep dive into them.

The result was: I focused on "what this thing should do," and Claude was responsible for "how to make this thing."

It's not that details aren't important. Rather, at this point, I believe that **having the idea and knowing something is broadly feasible is more valuable than figuring out all the details yourself**.

There's a simple test: If you can clearly articulate, "I want X, and this should be achievable through A → B → C," then you're already in a position to make it happen, whether you do it yourself, find someone else to do it, or work with AI.

Previously, without AI, this idea might have stayed in the 'idea' phase because I wouldn't want to spend time researching `feedparser` documentation or GitHub Actions permission settings. Now it's actually running, and I understand the entire pipeline; even if something goes wrong, I can determine which part is at fault.

This is what I currently feel is the smoothest mode of 'AI collaboration': you provide the direction, and it's responsible for turning that direction into something operational.
